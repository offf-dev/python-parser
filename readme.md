# Docker Compose

| Команда                                      | Что делает                                                              | Когда использовать                                                                                                  | Режим работы                  |
|----------------------------------------------|-------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|-------------------------------|
| `docker compose up`                          | Запускает контейнеры из уже существующих образов (без пересборки)       | Ничего не менял в коде/Dockerfile, просто поднять или перезапустить сервисы                                        | Foreground (логи в терминале) |
| `docker compose up fe-articles`              | Запускает только контейнер fe-articles | Ничего не менял в коде/Dockerfile, просто поднять или перезапустить сервисы                                        | Foreground (логи в терминале) |
| `docker compose up --build`                  | **Пересобирает** все образы → запускает контейнеры                      | Изменил код, Dockerfile, requirements.txt и т.д.                                                                   | Foreground                    |
| `docker compose up -d`                       | Запускает контейнеры **в фоне** (detached)                              | Хочешь запустить и отойти от терминала                                                                              | Background                    |
| `docker compose up -d --build`               | **Пересобирает образы + запускает в фоне** — САМАЯ ЧАСТАЯ КОМАНДА       | В 99% случаев: внёс любые изменения → одна команда всё пересобирает и поднимает                                     | Background                    |
| `docker compose up --build --force-recreate` | Пересобирает + **полностью пересоздаёт контейнеры** (удаляет старые)    | Глюки с томами, кэшем, сетью — нужно «с чистого листа»                                                                     | Foreground (или с `-d`)       |

## Ежедневные команды

```bash
# 1. Основная команда — после любых изменений
docker compose up -d --build

# 2. Просто перезапустить без пересборки (например изменился код или env)
docker compose up -d

# 3. Остановить всё
docker compose down
# с очисткой томов (если нужно):
docker compose down -v
```

# Локальные режимы работы fe-articles

База данных и Telegram-каналы у локалки и стейджа **общие** (Cityhost MySQL,
тестовый канал). Разница — пишем мы из локалки или нет.

## Read-only dev (по-умолчанию)

UI читает из боевой БД, ничего не пишет. Парсер автоматически отключён.
Удобно тестить новые фичи, ковыряться в шаблонах, играть с фильтрами —
ничего не сломаешь.

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d fe-articles
```

UI: http://localhost:5000/

## Local-write (для ручного парсинга)

Используется для сайтов, которые не парсятся со стейджа (Cloudflare и
прочая бот-защита) — у домашнего IP их обычно пропускает.

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml -f docker-compose.write.yml up -d fe-articles
```

После подъёма — выбери ID нужного сайта на `/sites` и запусти точечный
парсинг (active-флаг игнорируется, парсит даже выключенные источники):

```bash
# один сайт:
docker exec python-parser-fe-articles-1 python run_once.py 150

# несколько разом:
docker exec python-parser-fe-articles-1 python run_once.py 150 165 168
```

Скрипт прогоняет: parse_resource → English/blacklist/blocked-keywords
фильтры → URL-нормализация → дедуп против всех существующих `links` →
INSERT новых в БД. Прод-сервер дальше по своему trickle-расписанию
(каждые 3 мин) подхватит и отправит в канал.

После сессии — обратно в read-only:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d fe-articles
```

## Когда НЕ надо local-write

- Что-либо тестируешь и не хочешь чтобы случайные данные улетели в БД
- Делаешь refactor / правишь UI / пробуешь новый CSS
- Не уверен что код правильный

В обычной разработке всегда `dev` (read-only). `write` — только для
запланированной ручной заливки данных.

# Обслуживание сервера (парсер как «санитар»)

Репозиторий перестал быть только парсером: здесь же описана гигиена самого
сервера `135.181.254.225` (`fruntend-stage`, Hetzner CAX11, 38 ГБ диска).

**Почему это оказалось задачей парсера.** Машина общая — кроме нас на ней живут
`busygym-*`, `ukrsibbank-*` и `laravel_admin_*` (fruntend). Общий у них только
диск: когда он кончается, ложатся все сразу, независимо от того, чей процесс его
съел. А съедает его в основном парсер: каждый деплой пересобирает образ с
Playwright и Chromium, и каждая пересборка оставляет в кэше слой на ~1.2 ГБ.
03.09.2026 это привело к 85% занятого диска (5.4 ГБ свободно), из них 14 ГБ —
docker build cache. Поэтому присмотр за местом повесили на тот проект, который
его и расходует.

Версионируемые копии всех упомянутых ниже скриптов и крон-файлов лежат в
[`ops/`](ops/) — там же инструкция по установке. На сервере они живут на хосте,
а не в контейнере, и GitHub Actions их не выкатывает: ставятся руками.

## 1. Еженедельная чистка docker build cache

Файл `/etc/cron.d/docker-builder-prune` (копия: `ops/cron.d/docker-builder-prune`),
воскресенье 04:00 (сервер в `Europe/Kyiv`):

```
0 4 * * 0 root sh -c 'date -Is; docker builder prune -f --filter until=168h' >> /var/log/docker-builder-prune.log 2>&1
```

- `--filter until=168h` — удаляются только слои, к которым не обращались 7 дней.
  Кэш парсера под фильтр не попадает никогда: он пересобирается на каждом пуше
  в `main`. Соседям грозит максимум более долгая пересборка, если их не собирали
  больше недели.
- Образы, контейнеры, тома и `/var/www` не трогаются, ничего не
  перезапускается.
- **`docker system prune -a` здесь делать нельзя** — он снесёт неиспользуемые
  образы соседей.
- В `/etc/docker/daemon.json` уже есть GC-политика BuildKit с
  `defaultKeepStorage: 10GB`, то есть потолок был и до крона — просто слишком
  щедрый для диска на 38 ГБ. Крон держит кэш в районе 3–4 ГБ.

## 2. Ежечасный контроль ресурсов с алертом в Telegram

Скрипт `/usr/local/bin/server-health-alert.sh` (копия:
`ops/server-health-alert.sh`), крон `/etc/cron.d/server-health-alert`, запуск в
:17 каждого часа, лог `/var/log/server-health-alert.log`.

Проверяет три показателя и при выходе за пороги шлёт сообщение в админ-чат
парсера (`FRUNTEND_ERRORS`) ботом `@fruntend_errors_bot`:

| Показатель        | Порог                      |
|-------------------|----------------------------|
| Занято на `/`     | ≥ 80%                      |
| Доступная память  | < 300 МБ (из 3.7 ГБ)       |
| Занято swap       | ≥ 75%                      |

Решения, заложенные в скрипт, и зачем:

- **Токен и chat_id не хранятся в скрипте** — читаются из
  `services/fe-articles/.env` при каждом запуске. После ротации токена править
  в двух местах не нужно.
- **Антиспам:** пока состояние не менялось, повтор уходит не чаще раза в сутки.
  Иначе забитый диск генерировал бы 24 одинаковых сообщения за день, и их
  перестали бы читать.
- **Возврат в норму сообщается отдельным сообщением**, чтобы не гадать,
  починилось ли оно само.
- Состояние между запусками лежит в `/var/lib/server-health-alert.state`.

Проверить руками (ничего не сломает, при нормальных показателях просто
напечатает строку состояния):

```bash
ssh fruntend-stage /usr/local/bin/server-health-alert.sh
tail -5 /var/log/server-health-alert.log
```

Поменять пороги — переменные `DISK_WARN`, `MEM_AVAIL_MIN_MB`,
`SWAP_USED_MAX_PCT` в начале скрипта.

## 3. Разовые чистки 03.09.2026

- `docker builder prune --filter until=168h` — освободил **9.58 ГБ**
  (167 записей кэша → 70).
- Удалены три образа, не использовавшиеся ни одним контейнером и не
  упоминавшиеся ни в одном конфиге на сервере: `php:8.2-cli` (740 МБ, остался
  от разовых запусков; `ukrsibbank` собирается из `php:8.2-apache`),
  `alpine:latest` (13 МБ), `hello-world` (26 КБ, след от установки Docker).
  Общие базовые слои при этом остались у `ukrsibbank-web`, `nginx:alpine` и
  `busygym-*` — Docker считает ссылки и удаляет только то, что больше никем не
  используется.
- Итог: диск **85% → 59%**, свободно стало 15 ГБ вместо 5.4 ГБ.

## Что ещё не сделано

Оба пункта трогают не только наши сервисы, поэтому требуют отдельного решения:

- **Системный журнал занимает 3.6 ГБ.** `/etc/systemd/journald.conf` пустой,
  дефолт — до 10% раздела. Лечится `SystemMaxUse=500M` плюс разовый
  `journalctl --vacuum-size=500M`: ~3 ГБ сразу. Минус — журналы старше пары
  недель пропадут для всех на сервере.
- **json-логи контейнеров растут без лимита** (102 МБ, из них 77 МБ —
  `number-challenge`). Для наших сервисов чинится блоком `logging` с
  `max-size: 10m` и `max-file: 3` в `docker-compose.yml`; применится при
  следующем пересоздании контейнера, соседей не затронет.
